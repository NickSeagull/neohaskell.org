# NeoHaskell visual language

This repository owns this skill and its references. The visual language is developing. Preserve accepted choices while testing the parts that have not earned a reusable rule.

## Establish the brief

Read [authority and baseline](references/baseline.md), then the current surface record and implementation for the affected area. Follow the applicable skills in the repository's `AGENTS.md`; this skill coordinates visual decisions rather than replacing product positioning, terminology, teaching review, or Unslop.

State the visitor's intended outcome and the visual question in one sentence each. The homepage persuades a developer to explore NeoHaskell; documentation helps a reader understand or do something. Both express the same identity, with different density and reading rhythm. For a skill-structure discussion, use [the hosq comparison](references/hosq-comparison.md); it is research context, not NeoHaskell's style guide.

Classify each decision used by the task as owner-accepted, implemented, or proposed. Record its source and scope. An existing CSS value establishes what is rendered, not that the owner wants it preserved forever. A reviewer verdict establishes an inspected result, not owner acceptance. Resolve conflicting records against the latest applicable owner direction before treating them as review criteria.

## Develop a rule

1. Name the uncertain relationship: for example, how a persistent record differs from its current answer, or how the same diagram belongs in a sales section and a lesson. Choose the smallest real section that exposes it. Reuse the site's actual content and components.
2. Inspect the nearest accepted examples and extract the relevant qualities: hierarchy, spacing, shapes, meaningful connections, type, and material. Choose a concrete treatment within the authorized scope. Keep an unfamiliar idea provisional until it has rendered evidence.
3. Implement the treatment where implementation is requested. For a rule intended for both surfaces, compare one homepage use and one documentation use, including the narrow layout and both themes. Preserve semantic meaning while adapting composition; scaling a desktop diagram down is not a phone composition.
4. Apply [the review lenses](references/review.md). Repair findings by cause and inspect the affected result again. Follow the repository's three-failed-fixes rule when the premise needs replacement. Finish with a working, verified result when implementation is in scope.
5. Record the resulting rule in its existing owner: design rationale in `DESIGN.md`, surface-specific composition in its surface brief, values in the owning styles, and behavior in its component. Include scope, reason, evidence, and decision status. Consolidate superseded active guidance within the authorized edit. Keep experiment notes distinct from the canonical rule.

For a new language-wide decision, begin with the calibration set in the baseline reference. For a local refinement, select only the affected lenses and occurrences. Broader testing follows shared impact, not the number of critique roles available. A structural skill review does not establish visual quality or complete the calibration step.

## Return a decision

Give the selected treatment, visible evidence, unresolved uncertainty, and the next concrete experiment if exploration remains. For an implemented change, report the preview, affected checks, and local commit under `AGENTS.md`. Name the finding and its effect on the visitor instead of returning an unexplained aesthetic score.

Skill-only changes need structural validation and an instruction walkthrough; rendered acceptance applies when the interface changes. Keep all required references, future instruments, and fixtures inside this skill's directory. Add a measurement tool only when an observed recurring defect warrants it, and prove it detects the defect before relying on it.
