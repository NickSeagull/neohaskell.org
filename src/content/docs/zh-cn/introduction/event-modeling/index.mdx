回想[代码背后的工作](../#the-questions-that-change-the-software)中介绍的马克杯商店。接受订单会为顾客留出所订购的马克杯。要设计这个应用，我们需要连接完整的体验：顾客查看库存、订购马克杯，并得知商店是否接受了订单。

[保护变更并回答问题](../../learn/)介绍了各个部分：命令请求变更，事件记录已接受的事实，查询提供答案。

**事件建模把这些部分连接成一个人们可以共同审视的流程。** 它把屏幕、命令、事件和查询放在同一个模型中。各部分的连接会揭示信息从何而来、在哪里需要信息，以及哪些业务问题仍待回答。NeoHaskell 使用相同结构来组织开发，并将规范保留在代码中。

## 跟踪下单和取消 <a id="follow-an-order-and-a-cancellation" />

商店有三只可用的马克杯。店主希望顾客可以在发货前取消订单，并将马克杯退回可用库存。先从订购一只马克杯再取消的流程开始。

模型有两个**章节**：下单 和 取消订单。每个章节分成两个**切片**：一个通过命令和已接受的事件来更改状态；另一个通过查询提供库存答案。竖线分隔开发单元。顶部的每个箭头横跨属于其章节的切片。

<ShopEventModel />

订单被接受后，库存查询返回两只。取消后，查询返回三只。重复出现的 可用马克杯 节点表示流程这两个阶段的库存答案。

画出各部分的连接，也会暴露出这张初步草图尚未回答的问题。“添加取消”听起来像一个按钮。模型会追问其余行为：

- 取消命令从哪里获取订单标识？
- 什么条件会阻止发货后取消？
- 哪个答案会告诉顾客取消成功？
- 什么会通知员工停止准备该订单？

**每一个未回答的问题，都代表应用中尚未设计的一部分。** 店主和开发者可以在一起查看同一流程时解决这些问题，避免智能体或开发者把假设直接写进代码。

## 一次开发一个切片 <a id="develop-one-slice-at-a-time" />

**切片是开发单元。** “接受订单”有输入、决策和可观察的结果。其实现会检查请求数量和库存，规则则会规定何时接受或拒绝。“显示剩余库存”是职责不同的独立切片：下单后维护相应答案。

取消也按同样方式拆分。一个切片决定能否取消订单并记录结果。另一个切片提供更新后的库存答案。章节会把它们归入顾客体验的同一部分，但不会把它们变成一个实现任务。

一个**功能**会把相关章节归在一起。这里，Orders 功能包含 下单 和 取消订单。如果流程需要外部副作用，例如发送订单确认，集成也会有自己的切片。模型为每项任务安排位置，并展示它依赖的契约。

## 部署后冻结契约 <a id="freeze-the-contract-when-it-is-deployed" />

面向顾客的命令是一项承诺。`PlaceOrder` 的调用者依赖其接受的输入和行为。查询的使用者依赖它提供的答案。已记录事件的含义，则依赖其定义保持不变。

**NeoHaskell 的部署模型会在部署时冻结这些定义及其实现。** 已部署的命令、事件或查询不能在保持相同标识的情况下被悄然改写。新需求或经修正的决策，会作为新行为与已部署行为并存。

假设商店新增配送结账流程，要求在接受订单前提供联系方式。原有的自取结账使用 `PlaceOrder`，它只接受商品和数量。不要直接修改它，而是在开发过程中复制该功能，为变更后的行为取一个新名称，例如 `PlaceOrderWithContact`，并实现额外检查。也可以添加后缀。关键在于，新契约拥有自己的标识。

配送结账使用新契约，而自取订单继续使用原契约。NeoHaskell 将这种小而明确的扩展作为常规开发方式：复用现有结构，只更改预期行为，并检查相关规则。工作会集中在新需求上，不必追查被改动实现的每个调用者。

修复错误也遵循相同规则。如果 `CancelOrder` 错误地接受了已发货订单，就创建修正后的 `CancelUndispatchedOrder`，测试遗漏的情况，将调用者迁移到新命令，并禁用错误命令。冻结旧实现会保留已部署时的行为，但不要求继续开放有问题的入口。

## 逐步淘汰行为，无需为整个 API 版本化 <a id="retire-behavior-without-versioning-the-whole-api" />

**新旧契约可以并存，等待各自的使用者迁移。** 移动应用可以继续通过 `PlaceOrder` 提供自取服务，网站则通过 `PlaceOrderWithContact` 增加配送服务。库存查询和无关命令保留原有名称和契约。

这样一来，不必因为一个操作发生变化就把整个 API 复制到 `/v2`。每个变更的行为都有自己的标识。使用者准备好时再采用替代项，无需同时将所有操作迁移到新 API 版本。

当不应再让新使用者选择某个旧命令或查询时，将其标记为**已弃用**。用量表明无人再调用后，就禁用或移除此入口。淘汰命令不会抹除它记录的事件，也不会移除解释这些历史所需的定义。

## 为什么更改共享代码会增加工作量 <a id="why-changing-shared-code-creates-more-work" />

想象在传统应用中，商店通过修改现有的 `POST /orders` 端点和共享的 `Order` 模型，来加入配送联系方式要求。把新字段设为必填会破坏旧的移动端结账流程。再把字段加入共享模型，就会影响订单编辑器和员工页面，尽管它们都没有要求改变订购策略。

接着，商店把取消从是非标志改为一种状态，用来区分已请求、已接受和已拒绝。以前检查 `cancelled` 的代码，现在都需要检查发货、库存计算和顾客邮件。一个小小的业务请求会扩散到多个功能，因为它们都在解释同一个可变模型。

**代价还包括重新检查已经正常工作的行为。** 在这张示意图中，A 到 G 表示新增到应用的内容。每个 R 都表示在早先行为中重复进行的工作。上升曲线表示随着依赖关系累积，每次变更所需的工作越来越多。

## 让增长保持接近线性 <a id="keep-growth-close-to-linear" />

在 NeoHaskell 中，配送联系方式要求会在被冻结的订购契约旁边增加一个命名命令及其规则。旧结账流程保持原有行为。新取消策略同样会得到明确的切片和契约；受影响的查询和集成则会显示在事件模型中。

**稳定的契约可以避免新需求悄然改变每个现有使用者的行为。** 切片限定实现工作范围，章节保留业务背景，模型则展示新行为如何连接到应用的其他部分。NeoHaskell 提供常用结构，因此创建替代项比反复梳理共享代码更省力。

<GrowthComparison mode="bounded" />

每次新增的工作量大致持平，因此总开发工作量会接近线性增长：再添加一个相似的切片，就增加一份相近的工作。这正是 NeoHaskell 旨在支持的开发方式。

取消行为仍必须与发货流程约定何时可以取消订单。这项约定属于受影响切片的契约和规则。开发者可以明确指出、检查并测试这种依赖，而不必等到顾客流程出错后才发现。

## 用模型理解代码 <a id="use-the-model-to-understand-the-code" />

**NeoHaskell IDE 会展示应用的结构。** 打开一个功能即可查看它的章节和切片，然后跟踪命令、事件、查询与集成之间的连接。你可以在实际 IDE 界面中探索马克杯商店模型：

<IdeScreenshot />

要更改取消行为，可以从 Cancel order 章节入手。找到发出取消请求的命令、它产生的事件，以及使用该事件的库存查询。这些名称能帮助你定位源代码中的对应声明。接手现有项目或审查 AI 智能体编写的变更时，也可以使用相同路径。

可视模型由源码声明生成。声明变更时，IDE 会刷新模型。重命名命令或新增查询连接都属于应用结构的一部分，因此会自动显示在图中，无需另行手动维护一张图。

## 将规范保留在应用中 <a id="keep-the-specification-in-the-application" />

**规范是代码的一部分。** NeoHaskell 的事件模型 DSL 会声明功能、章节、切片、命令、事件、查询和集成。切片旁的规则会描述其所需行为，包括 Given、When、Then 案例。

以下是商店模型中的取消章节。示例使用商店的 `Order`、命令、事件和查询类型，这些类型已在其他位置定义：

```haskell
orders =
  feature "Orders" do
    chapter "Cancel order" do
      slice "Cancel before dispatch" do
        entity @Order do
          command @CancelOrder do
            produces @OrderCancelled

        rule "Cancel before dispatch" do
          orderId <- requestValue @Uuid
          given do
            event OrderPlaced {
              orderId = orderId,
              quantity = 1
            }
          when CancelOrder { orderId = orderId }
          therefore do
            event OrderCancelled {
              orderId = orderId,
              quantity = 1
            }

      slice "Show restored stock" do
        query @AvailableMugs do
          readsFrom @Order do
            onEvent @OrderPlaced
            onEvent @OrderCancelled
```

**图中的层级就是代码中的层级。** 该章节包含一个命令切片和一个查询切片。`produces` 声明命令的事件；`readsFrom` 和 `onEvent` 声明为查询提供数据的历史。库存查询会同时监听已下单和已取消的事件，因此答案能够反映两种变更。

规则位于它所描述的命令旁。`requestValue` 会向规则运行器请求一个带类型的示例订单标识。`given` 提供已接受订单的历史，`when` 提供取消命令，`therefore` 则对应 DSL 中的 Then：预期的 `OrderCancelled` 事件。决策实现因此有一个明确案例需要满足。

第二条规则会涵盖已发货订单：取消必须被拒绝，库存必须保持不变。库存查询切片则会单独检查，已接受的取消是否恢复了可用库存数量。每个案例都应归属于它描述的行为。

独立的 Markdown 文件或 Confluence 页面可能会过时，因为应用变更后还得有人更新它。在 NeoHaskell 中，已声明的模型和规则本来就存放在源码中。描述这份规范的文档可以从这些声明生成，而不必成为另一份需要维护的权威资料。
