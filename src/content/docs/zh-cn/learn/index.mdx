[保留数字背后的事实](/introduction/history/#record-what-happened)中的马克杯商店会把已接受的订单记录为事件，并据此计算可用库存。

事件是应用已接受的一条事实。因此，事件周围的边界很重要：顾客不能只通过发送 `OrderPlaced` 事件，就宣称商店接受了订单。

假设顾客在只剩三只马克杯时要求订购四只。**请求下单与订单被接受，是两件不同的事。** 应用需要一种方式来接收请求、检查请求，并在不消耗库存的情况下拒绝请求。

## 用命令请求变更

**命令**表达了改变应用状态的意图。`PlaceOrder` 携带了下单所需的信息。订购一只马克杯时，信息如下：

```haskell
PlaceOrder {
  product = "ceramic mug",
  quantity = 1
}
```

**决策**会根据当前状态和商店策略评估命令。数量必须为正数，库存也必须充足。库存有三只时，订购一只会通过，订购四只则会失败。

<EventModelTour kind="decision" />

接受命令后会记录 `OrderPlaced`。拒绝命令会让库存保持不变，也不会记录 `OrderPlaced` 事件。**命令携带意图；事件记录已接受的事实。**

NeoHaskell 提供执行路径：获取相关状态、评估决策，然后追加已接受的事件。开发者编写表达商店承诺的条件。网站和 AI 工具可以提交相同的命令，并使用相同的决策。

## 让业务决策保持纯

**NeoHaskell 将纯代码置于应用开发的核心。** 业务逻辑会根据收到的信息描述应该发生什么。决策检查命令和当前状态，然后描述接受或拒绝。它不能打开数据库连接、发送确认邮件或调用支付提供方。

对于商店的库存规则，相同订单和可用库存会产生相同的接受或拒绝结果。测试库存为三时能否订购四只马克杯，并不会在数据库中创建订单。这只是在计算决策的答案。

这一边界会改变日常开发：

- **测试数千种情况，不产生外部影响。** 生成不同库存和请求数量的组合，包括零、负数和最后一只可用的马克杯。无需数据库、网络连接或邮箱账户，就能检查决策。
- **重现故障。** 保留暴露库存规则错误的输入，并再次运行。调查该规则不依赖提供方是否可用，也不依赖测试数据库中是否有正确内容。
- **依据可观察行为进行重构。** 让新旧库存规则使用相同案例，并比较各自的决策。手写或由 AI 智能体编写的变更，都可以根据商店的承诺进行检查。
- **更换基础设施，无需重写策略。** 库存规则不包含 SQL 或邮件提供方调用。更换存储或邮件服务，不会改变接受订单的条件。
- **理解并复用逻辑。** 直接查看输入和最终决策，无需追查其他服务中隐式发生的写入。抽取计算或复用规则时，也无需连带数据库连接。

**在 NeoHaskell 中，纯应用逻辑是常规做法。** 开发者编写规则和计算；语言提供加载状态和记录已接受变更的机制。测试业务行为时，不必让这些机制围绕每条规则运行。

## 应用如何完成实际工作？

已接受的订单仍然需要确认邮件。**集成会执行应用逻辑之外的副作用。** 它们会将这项工作独立封装，让商店的决策不依赖执行任务的提供方。

集成工作器知道如何完成自己的任务。邮件工作器接收收件人和消息并发送邮件。它不决定订单是否获准、还剩多少库存，或哪些顾客应该收到确认。这些选择属于应用的纯逻辑。

记录 `OrderPlaced` 后，应用可以请求执行这项工作。如果邮件提供方不可用，订单仍然是已接受的。改变邮件的发送方式会改变集成，而不是库存策略。[集成指南](/guides/integrations/)介绍了如何配置和运行这些工作器。

## 为每个屏幕提供所需答案

订单被接受后，不同的人需要不同的答案。下一位顾客需要知道可用库存；顾客本人需要确认信息；员工需要知道还有多少订单等着处理。

读取库存答案不会再下一笔订单。每次访问页面时，也无需扫描完整事件历史：NeoHaskell 会在变更到达时更新查询状态，屏幕读取的是已维护的答案。

**同一组事实可以支持不同问题。** 顾客界面和员工报表可以采用不同的数据形状，而无需各自维护彼此冲突的事实记录。新报表也可以利用保留的历史计算另一种答案。

屏幕显示的答案可能落后于刚发生的变更。因此，屏幕上的库存不能作为下单许可：请求到达时，命令的决策会检查相关状态。

将变更与问题分开处理，称为 **CQRS**。命令和决策控制哪些事情可以发生；查询则整理人们需要了解的信息。事件溯源提供了应用推导状态所需的历史。
