Consider the mug shop introduced in [The work behind the code](/introduction/#the-questions-that-change-the-software). Accepting an order sets aside the requested mugs for the customer. To design its application, we need to connect the whole experience: a customer sees stock, orders a mug, and finds out whether the shop accepted the order.

[Protect changes and answer questions](/learn/) explains the individual parts: a command requests a change, an event records an accepted fact, and a query supplies an answer.

**Event Modeling connects the parts into a process people can examine together.** It puts screens, commands, events, and queries in one model, showing where information comes from and where it is needed. A missing connection becomes a question to resolve with the people running the business.

## Follow an order and a cancellation

Consider the next request from the shop owner: customers should be able to cancel before dispatch, returning their mugs to available stock. Start with a first sketch of that journey, from ordering one mug to cancelling it.

<ShopEventModel />

The order command leads to an accepted order event. The stock query then answers two. Cancellation needs the identity of the order; the stock answer alone does not supply it. After acceptance, an event records the cancellation and the stock answer returns to three.

This is where drawing the connections earns its place in the work. "Add cancellation" sounded like a button. The model asks for the rest of the behavior:

- Where does the cancellation command get the order identity?
- What prevents cancellation after dispatch?
- Which answer tells the customer that cancellation succeeded?
- What tells staff to stop preparing that order?

**Each unanswered question is a piece of the application that has not been designed yet.** The owner and the developer can resolve it while looking at the same process, before an agent or a person turns an assumption into code.

## Give a change a clear boundary

Cancellation has a recognizable set of responsibilities: request the action, check whether it is allowed, record the outcome, and update the answers people use. That gives the developer concrete behavior to implement and cases to test.

It also exposes the shared agreement with dispatch. Once an order has been dispatched, cancellation must be refused. Placing those behaviors in the same model makes the dependency visible instead of leaving two features to define "cancelled" independently.

## Keep growth close to linear

Hidden dependencies make an application progressively harder to change. A new behavior requires adjustments to older behaviors, and those adjustments uncover more assumptions. The work grows beyond the feature being added.

**Event Modeling aims to keep added behavior a bounded piece of work.** When its inputs, outcomes, and shared contracts are visible, the team can identify what needs to change and what needs testing. Similar additions can then take similar effort, so total effort grows roughly with the number of behaviors.

In the comparison, A through G represent added behaviors. Each R is rework in an earlier behavior. The second plot shows the intended growth pattern when slices and their shared contracts remain visible.

Cancellation and dispatch show what that requires in practice. Their shared order status must agree, so a change to dispatch needs a check against cancellation. Drawing that connection gives the team a specific dependency to manage. The curves illustrate these two ways of accumulating work; they are not benchmark measurements.

## Use the model to understand the code

NeoHaskell carries these concepts into typed application declarations. Its visual IDE reads the source model and displays the relationships between behaviors. **The model remains useful after the application has been built.** It helps locate a behavior in an unfamiliar project and examine what an agent has changed.

For a cancellation change, that means finding the command, the decision that prevents cancellation after dispatch, the recorded outcome, and the queries that should reflect it. The model guides inspection; tests check the concrete cases: cancellation before dispatch restores stock, and cancellation after dispatch is refused.

The developer can discuss the policy with the shop owner, locate its implementation, and judge a generated change using the same business concepts. That connection is how NeoHaskell keeps a whole application within one person's understanding as its implementation grows.
