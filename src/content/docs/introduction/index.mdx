<p class="docs-lead">See what your application does. Agree what should change. Give the next behavior a clear place to belong.</p>

The most useful conversation starts with the work people need to do. A shop owner wants customers to order ceramic mugs. You help turn that intention into a story the owner, the developers, and a coding agent can all follow.

The shop starts with three mugs and no orders. For this example, accepting an order immediately uses the requested stock. A customer orders one:

<EventModelTour kind="story" />

This picture already makes a business choice visible: stock changes when the order is accepted. Choosing a different moment, such as payment, would change the application. Agreeing that behavior is part of designing the software.

**Event Modeling** gives these conversations a common visual language. It connects what people want to do, the facts that follow, and the information they need next. The same picture helps you plan a new application or understand one that already exists.

## Separate an intention from what happened

A **command** expresses an intention: order one mug. It gives the application something to consider. The command alone does not mean an order exists.

A **decision** checks the conditions for accepting it. Here, the quantity must be positive and enough stock must be available. With three mugs in stock, an order for one passes those checks.

An **event** records the accepted fact: an order for one mug was placed. Its name describes something that has happened, so other parts of the application can use that fact.

<EventModelTour kind="decision" />

If the shop has no mugs, the same command is rejected. No order-placed event is recorded and stock stays at zero. Drawing that boundary helps everyone distinguish a customer's intention from a promise the shop has actually made.

## Turn recorded facts into useful answers

After accepting the order, the customer needs confirmation and the next visitor needs the remaining stock. A **query** answers a question from the application's state without changing it.

The recorded order tells us one mug was taken from the opening stock of three. We can use that fact to answer different questions:

<EventModelTour kind="queries" />

The event remains part of the history. The answers can change as more orders are accepted. This separation lets you trace a displayed number back to the behavior that produced it, and decide what information a new screen needs.

Payment and delivery are outside this first order story. Each can become another behavior with its own intentions, decisions, facts, and answers.

## Keep growth close to linear

As an application grows, hidden dependencies can turn one new feature into changes across several old ones. Event Modeling aims to keep growth closer to linear: add a small behavior with explicit inputs and outputs, then use the same pattern again.

We call one of these bounded behaviors a **slice**. Placing, cancelling, and dispatching an order are different slices. Each has its own decision and outcome. Cancellation and dispatch share an order's identity and status, and must agree on what cancelled means.

<EventModelTour kind="growth" />

The useful unit of work becomes one behavior you can explain and test. You can discuss cancellation without reopening every detail of ordering, and give an agent a focused change with a checkable result.

That depends on clear boundaries and stable shared contracts. Changing what an order means can still affect several slices. The model makes that coordination visible so the team can plan it, rather than discover it accidentally while changing code.

## Use the model to understand what you already have

In an existing application, follow one real task through the same four questions: what was asked, which conditions were checked, what happened, and what information was shown afterward.

Put the business explanation beside the application's actual behavior. A disagreement becomes specific: perhaps the shop owner expects a cancellation to restore stock, but the current application only changes the order status. The model gives both sides a precise place to discuss the missing behavior.

Your contribution is turning assumptions into shared, testable decisions. An AI agent can help implement them; the people who understand the business decide what those decisions should be.

## Carry the picture into NeoHaskell

NeoHaskell is an AI-first language and framework built around commands, decisions, events, and queries. These become explicit parts of the application. Its visual IDE shows their relationships, so you can inspect the model while understanding or changing the software.

Event Modeling supplies the shared design. Event Sourcing supplies a way to retain events and derive state from their history. You can understand the design before choosing storage or installing tools.
