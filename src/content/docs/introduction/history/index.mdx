The shop's questions determine what the application needs to remember. Consider an accepted order: the shop starts with three mugs, and accepting an order for one commits that mug to the customer. Two remain available.

<EventModelTour kind="story" />

The stock number gives the next customer a useful answer. **It does not explain why that answer changed.** A broken mug would also reduce stock from three to two, but it would not give the shop an order to prepare.

## Record what happened

Saving only the latest stock value loses that distinction. NeoHaskell records the business fact that caused the change: an order was placed for one ceramic mug. This recorded fact is an **event**.

The event's name carries meaning. `OrderPlaced` tells the application that the shop accepted an order. Breakage needs a different event because it represents different work, even when the effect on available stock is identical.

| Information retained | What it establishes |
| --- | --- |
| Current stock: 2 | Two mugs are available now. |
| Stock snapshots: 3, then 2 | Stock decreased by one. |
| Order placed: 1 ceramic mug | An order was accepted; the shop has an order to prepare. |

Keeping versions of the stock value preserves the difference between two numbers. **Recording events preserves the business meaning of the change.** The developer chooses that meaning explicitly instead of leaving someone to reconstruct it later.

## Calculate the present from the past

In NeoHaskell, **events are the source of truth for application state**. Starting with the shop's opening stock of three, applying the accepted order for one produces the current stock of two. Deriving state from recorded events is called **Event Sourcing**.

Suppose the customer then cancels before dispatch, and the shop returns the mug to available stock. The application records `OrderCancelled`, bringing availability back to three. It keeps the original order event as well. An order that was cancelled is a different history from an order that never existed.

Corrections follow the same principle: record the correction and apply its effect. Changing the present does not require rewriting the account of how it happened.

This history also makes calculations repairable. If a stock calculation contains a bug, fixing it and applying the history again rebuilds the derived state. **Replay recalculates state**; it does not place the order or charge the customer again.

## A snapshot saves a calculation

Recalculating from the first event on every operation would repeat work. NeoHaskell uses **snapshots** to save derived state at a known point in the history, then applies later events from there.

A snapshot answers what the state was at that point. Events explain the business changes that led to it. Saving more versions of a stock number cannot recover a reason that was never recorded.

## Keep the facts future questions need

With order and cancellation events, the shop can distinguish sales from cancellations even when both leave the same final stock as no activity at all. It can investigate an order or build a new report from those recorded facts.

That makes event design part of understanding the business. If staff need to know who approved an exception, the event must retain that information. **The useful question is what someone will need to explain later.** Its answer determines what the application remembers today.
