A customer asking for four mugs has not created an order for four mugs. With only three available, the shop must refuse that request without consuming stock or recording an accepted order.

## Put the decision before the fact

The application therefore exposes a way to ask for an action, rather than letting a caller declare that the action already happened. A **command** carries that request. This plain-text example shows the information in `PlaceOrder`:

```text
PlaceOrder
  product: ceramic mug
  quantity: 1
```

A **decision** evaluates the command against the relevant current state and the shop's conditions. The event history belongs behind this boundary: a customer can request an order, but cannot make the shop accept it simply by submitting an `OrderPlaced` fact.

For this example, the quantity must be positive and enough stock must remain. An order for one passes when three are available. An order for four fails.

<EventModelTour kind="decision" />

If accepted, the application records `OrderPlaced`. If rejected, it records no `OrderPlaced` event and leaves stock unchanged. Naming the intention and the fact separately prevents a submitted form from being mistaken for a promise the shop has accepted.

Validation can be written in any language. NeoHaskell supplies the execution path around it: obtain the relevant state, evaluate the decision, and append the accepted events. The decision API separates business logic from external actions such as sending an email or charging a payment. Those actions belong in **integrations**. The stock decision can be tested with a command and state without contacting a payment service.

The same behavior can then serve different interfaces. A website and an application command line can submit the same command instead of each implementing their own stock policy. An agent helps write that policy; it does not decide at runtime whether the customer deserves a mug.

## Give questions their own answers

The customer needs order confirmation. The next shopper needs available stock. Staff may need the number of accepted orders.

A **query** maintains useful state derived from the application and exposes an answer to a caller. In the example, the accepted order reduces the stock answer from three to two and increases the order count from zero to one.

<EventModelTour kind="queries" />

Reading the answer does not place or cancel an order. The application does not need to scan the complete history for every page visit. Query state can be updated as changes arrive, so the stock question reads the maintained stock answer. The event remains the recorded fact; the query's state is a way of using those facts.

Separating these responsibilities means a staff report can have a different shape from the customer's stock display, while both use the same recorded business facts. A new report can be built from retained history if that history contains the information it needs. A query that is still catching up may return an older answer, so the application must account for that in the screen it shows.

Separating the handling of changes from the handling of questions is called **CQRS**. Event Sourcing concerns the history used to derive state; CQRS concerns these different responsibilities.
