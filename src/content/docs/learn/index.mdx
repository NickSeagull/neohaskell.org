The mug shop in [Keep the facts behind the numbers](/introduction/history/#record-what-happened) records accepted orders as events and uses them to calculate available stock.

An event is a fact the application has accepted. That makes the boundary around it important: a customer cannot declare that the shop accepted an order simply by sending an `OrderPlaced` event.

Consider a customer asking for four mugs when only three remain. **Asking for an order and having an accepted order are different things.** The application needs a way to hear the request, check it, and refuse it without consuming stock.

## Ask for a change with a command

A **command** expresses an intention to change the application. `PlaceOrder` carries the information needed to request an order. For one mug, that information looks like this:

```text
PlaceOrder
  product: ceramic mug
  quantity: 1
```

A **decision** evaluates that command against the current state and the shop's policy. The quantity must be positive, and enough mugs must be available. With three in stock, an order for one passes and an order for four fails.

<EventModelTour kind="decision" />

Acceptance records `OrderPlaced`. Rejection leaves stock unchanged and records no `OrderPlaced` event. **The command carries the intention; the event records the accepted fact.**

NeoHaskell supplies the execution path: obtain the relevant state, evaluate the decision, and append the accepted events. The developer writes the conditions that express the shop's promise. A website and an AI tool can submit the same command and use that same decision.

## Keep external work out of the decision

Accepting an order may also require sending a confirmation email. That work has a different failure mode: the shop can have accepted the order even while its email provider is unavailable.

NeoHaskell separates business decisions from these external actions. **Integrations** connect application behavior to external work. An outbound integration can react to `OrderPlaced` and send the confirmation. An inbound integration can introduce a command from an external source.

This separation gives the stock policy a focused test: supply a command and current state, then check whether the decision accepts or rejects it. No email provider or payment service is needed to find out whether four mugs can be ordered from a stock of three.

## Give each screen the answer it needs

Once the order is accepted, different people need different answers. The next shopper needs available stock. The customer needs confirmation. Staff need to know how many orders await their attention.

Reading the stock answer does not place another order. It also does not require scanning the complete event history for each page visit: NeoHaskell updates query state as changes arrive, and the screen reads that maintained answer.

**The same facts can support different questions.** A customer display and a staff report can have different shapes without needing competing accounts of what happened. A new report can use the retained history to calculate another answer.

A displayed answer can lag behind a new change. That is why the stock shown on a screen is not permission to place an order: the command's decision checks the relevant state when the request arrives.

Separating changes from questions is called **CQRS**. Commands and decisions control what may happen; queries organize what people need to know. Event Sourcing supplies the history from which the application derives its state.
