在庫数を見れば、次のお客様にマグカップがいくつあるかを伝えられます。**イベントは、数が変わった理由を説明します。**

[コードの背後にある仕事](../#the-questions-that-change-the-software)で紹介したマグカップ店を考えてみましょう。ネット注文を求められたことをきっかけに、店がお客様に何を約束するのかという問いが生まれました。

この店にはマグカップが3個あります。1個の注文を受理すると、その1個はお客様のために確保され、残りは2個になります。

<EventModelTour kind="story" />

在庫数は次のお客様に役立つ回答を返します。**しかし、その答えが変わった理由は説明しません。** マグカップが壊れても在庫は3個から2個に減りますが、店が準備すべき注文は発生しません。

## 起きたことを記録する <a id="record-what-happened" />

最新の在庫数だけを保存すると、この違いが失われます。NeoHaskellは変更の原因となった業務上の事実、つまり陶器のマグカップ1個の注文が入ったことを記録します。この記録された事実が**イベント**です。

イベントの名前は意味を持ちます。`OrderPlaced`は、店が注文を受理したことをアプリケーションに伝えます。マグカップの破損は在庫数への影響が同じでも別の作業を表すため、異なるイベントが必要です。

**イベントを記録することで、変更の業務上の意味を保てます。** 後から誰かが在庫数から理由を推測するのではなく、開発者が意味を明示的に選びます。

## 過去から現在を計算する <a id="calculate-the-present-from-the-past" />

NeoHaskellでは、**アプリケーション状態の情報源はイベントです。** 利用可能な在庫を計算するには、マグカップがない状態から始めて、起きたことを順にたどります。店に3個届き、その後1個の注文を受理したので、残りは2個です。記録されたイベントから状態を導出する方法を**Event Sourcing**と呼びます。

その後、お客様が発送前に注文をキャンセルし、店がマグカップを在庫に戻したとします。アプリケーションは`OrderCancelled`を記録し、在庫数は3に戻ります。それでも元の注文イベントは保持します。キャンセルされた注文の履歴と、注文が一度もなかった履歴は異なります。

<EventHistoryReplay />

訂正も同じ原則に従います。訂正を記録して、その効果を適用します。起きた経緯の記録を書き換えなくても、現在の状態を変更できます。

この履歴があれば、計算を修正できます。在庫計算にバグがあれば、修正して履歴を適用し直すことで導出状態を再構築できます。**リプレイで状態を再計算します。** 注文や請求をもう一度実行するわけではありません。

## 履歴が増えると遅くなりませんか。 <a id="wont-this-get-slow-as-the-history-grows" />

アプリケーションを使うほど履歴は増えますが、**NeoHaskellは操作のたびに最初のイベントから処理し直すわけではありません。** すでに計算した状態を保持し、そこから後続の変更を適用します。ページを開くたびに履歴全体をリプレイせず、維持されたデータから回答を読み取れます。

こうした処理は内部で行われます。アプリケーションは起きたことの記録を保持し、新しい注文のたびにそれ以前のすべての注文を再計算することはありません。

## 将来の問いに必要な事実を残す <a id="keep-the-facts-future-questions-need" />

注文とキャンセルのイベントがあれば、最終的な在庫数が何もなかった場合と同じでも、販売とキャンセルを区別できます。記録された事実から注文を調べたり、新しいレポートを作成したりできます。

そのため、イベントの設計には業務への理解が必要です。スタッフが例外を誰が承認したか知る必要があるなら、その情報をイベントに残します。**後から説明が必要になることは何か。それを考えるのが役立ちます。** その答えによって、アプリケーションが今記憶すべきことが決まります。
