**開発者の価値は、APIを暗記したり構文を正しく書いたりすることではありません。** 問題を理解し、解決するものを作ることにあります。そのためには、問いを投げかけ、矛盾を見つけ、ソフトウェアの要件を変える細部にまで目を向ける必要があります。

AIによって実装を書くのは簡単になります。そのぶん、判断の価値は高まります。短い説明からエージェントがチェックアウト画面を作れても、ボタンを押したときに店が何を約束するか決めるには、業務への理解が必要です。

NeoHaskellは、この開発の考え方を軸に作られています。**一人でアプリケーション全体を理解して作れるべきです。** ツールはその人の判断を支え、開発を楽しいものにします。そのため、アプリケーション作りに必要なツールを言語に組み込み、AIを設計の中心に据えています。

## ソフトウェアを変える問い <a id="the-questions-that-change-the-software" />

店主がネット注文をしたいと考えています。棚には陶器のマグカップが3個あります。開発者が1個買うことの意味を問い始めると、依頼は単純ではなくなります。

- マグカップを買い物かごに入れた時点で、ほかのお客様には売れなくなるのか。
- 支払いを受けた時点と注文を受理した時点のどちらで、店はマグカップを約束するのか。
- 注文がキャンセルされたら、いつマグカップを再び購入可能にするのか。
- 残りの在庫を超える数量をお客様が注文したら、どうするのか。

こうした問いはチェックアウト画面の先に及びます。お客様の期待を、注文を梱包する人の作業や返金を担当する店主の仕事につなぎます。工程の異なる時点を、関係者が同じ「注文」という言葉で呼んでいることもあります。

**意見の違いを見つけて解消することが、ソフトウェア開発です。** 答えによって、アプリケーションが記憶すべきこと、防ぐべきこと、それぞれの人に伝えるべきことが決まります。問いを立てずにコードを書くと、言葉にされていない業務上の判断を実装の中に隠してしまいます。

これは簡単な仕事ではありません。相手の話を聞き、思い込みに異議を唱え、例外まで工程を追う必要があります。エージェントを使うと、理解したことを実装に移しやすくなります。成果を価値あるものにするのは、その理解です。

## 組み立て作業を引き受ける言語 <a id="a-language-that-takes-on-the-assembly-work" />

判断に集中できる環境が必要です。変更の保存方法、ライブラリの接続方法、新しいフィーチャーの整理方法を毎回選ぶことに時間を使うと、アプリケーションそのものにかける時間が減ります。

NeoHaskellは、繰り返し必要になる技術的な選択を引き受けます。変更案を確認し、何が起きたかを記録し、画面に表示する回答を更新するための共通の方法を提供します。開発者は店の方針を定義し、NeoHaskellがそれを適用する仕組みを提供します。

たとえば、ウェブサイトやAIツールから注文を受けても、在庫の方針の実装は1つであるべきです。NeoHaskellでは、どちらのインターフェースからも同じ業務上の判断を通ります。インターフェースを増やしても、方針を適用する場所を新たに作る必要はありません。

**便利なアプリケーションを作るのに、一人であらゆる層の専門家にならなくてよいよう、こうした機能を言語に組み込んでいます。** 共通の規約があると、エージェントは一貫した構造に沿って作業でき、開発者は同じ構造を使って変更を確認できます。

## 筋の通ったものを作る楽しさ <a id="enjoy-building-something-that-makes-sense" />

NeoHaskellでは、開発者の喜びを設計上の優先事項としています。難しいプロセスを整理し、明確に表現して、意図したとおりにアプリケーションが動くのを見ることには喜びがあります。ツールによって、その仕事にもっと集中できるようにします。

業務への理解を実装に近づけるため、NeoHaskellでは**Event Modeling**という手法を使います。人々がしたいこと、実際に起きること、その後に見たい情報をつなぎます。同じ概念でアプリケーションを整理するため、店主と合意した考え方をコード内の対応する場所で確認できます。

エージェントが実装を書く場合も、開発者が手作業で書く場合も、結果を判断する根拠は具体的なままです。お客様の依頼、店の約束、合意した動作です。だからこそ、生成された変更を開発者が理解し、責任を持てます。
