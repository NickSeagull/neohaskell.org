[コードの背後にある仕事](/introduction/#the-questions-that-change-the-software)で紹介したマグカップ店を考えてみましょう。注文を受理すると、要求されたマグカップをそのお客様のために確保します。アプリケーションを設計するには、お客様が在庫を見て、マグカップを注文し、店が受理したかどうかを知るまでの体験全体をつなぐ必要があります。

[変更を保護し、質問に答える](/learn/)では、個々の要素を説明しています。コマンドは変更を要求し、イベントは受理された事実を記録し、クエリは回答を返します。

**Event Modelingは、これらの要素を、人々が一緒に検討できるプロセスとしてつなぎます。** 画面、コマンド、イベント、クエリを1つのモデルにまとめます。つながりを見ると、情報の出どころ、必要とされる場所、まだ答えのない業務上の問いがわかります。NeoHaskellでは、同じ構造で開発を整理し、仕様をコードに保ちます。

## 注文とキャンセルの流れを追う

ショップにはマグカップが3個あります。店主は、発送前ならお客様が注文をキャンセルでき、マグカップを在庫に戻せるようにしたいと考えています。マグカップを1個注文し、その後にキャンセルする流れから始めましょう。

モデルには「注文する」と「注文をキャンセル」の2つの**チャプター**があります。各チャプターは2つの**スライス**をまとめます。1つはコマンドとその受理イベントで状態を変更し、もう1つはクエリで在庫数を返します。縦線は開発単位を分けています。上部の矢印は各チャプターに属するスライスをまたいでいます。

<ShopEventModel />

注文が受理された後、在庫クエリは2と答えます。キャンセル後は3と答えます。「利用可能なマグカップ」のノードを繰り返し示すことで、プロセスの2つの時点における在庫の回答を表しています。

つながりを描くと、この最初のスケッチで未回答の点も見えてきます。「キャンセル機能を追加する」という依頼は、ボタンの話に聞こえました。しかしモデルは、動作全体を問います。

- キャンセルコマンドは注文の識別子をどこから得るか。
- 発送後のキャンセルをどう防ぐか。
- キャンセル成功をお客様に知らせる回答はどれか。
- スタッフに、その注文の準備を止めるよう伝えるのは何か。

**未回答の問いは、まだ設計されていないアプリケーションの一部です。** エージェントや人が仮定をコードにする前に、店主と開発者が同じプロセスを見ながら答えを決められます。

## スライスごとに開発する

**スライスは開発の単位です。** 「注文を受理する」には入力、判断、観測可能な結果があります。実装では要求数量と在庫を確認し、ルールで受理または拒否する条件を決めます。「残りの在庫を表示する」は、別の役割を持つスライスです。注文が入った後の在庫回答を維持します。

キャンセルも同じように分けられます。一方のスライスは、注文をキャンセルできるか判断して結果を記録します。もう一方は更新後の在庫数を返します。チャプターでは、お客様の体験の一部としてまとめますが、実装タスクは分けます。

関連するチャプターは**フィーチャー**にまとめます。この例ではOrdersフィーチャーに、注文すると注文をキャンセルのチャプターがあります。注文確認の送信など外部処理が必要なら、統合には専用のスライスを設けます。モデルによって各タスクの場所と、それが依存する契約がわかります。

## デプロイ時に契約を固定する

お客様が使うコマンドは約束です。`PlaceOrder`の呼び出し元は、受け付ける入力と動作に依存します。クエリの利用者は、そのクエリが返す回答に依存します。記録されたイベントは、事実の意味を保つ定義に依存します。

**NeoHaskellでは、デプロイした定義とその実装を固定します。** デプロイ済みのコマンド、イベント、クエリを、同じ識別子のまま黙って書き換えることはできません。新しい要件や修正した判断は、デプロイ済みの動作と並ぶ新しい動作になります。

たとえば、ショップで注文を受理する前に連絡先が必要な配送注文を追加するとします。既存の店頭受け取りでは、商品と数量だけを受け取る`PlaceOrder`を使います。既存の実装をその場で編集せず、開発中のフィーチャーを複製し、`PlaceOrderWithContact`のような新しい名前を付けて、追加の確認を実装します。末尾にサフィックスを付ける方法もあります。重要なのは、新しい契約が独自の識別子を持つことです。

配送注文には新しい契約を使い、店頭受け取りは元の契約を使い続けます。NeoHaskellでは、小さく明示的な追加を通常の開発手順にします。確立された構造を再利用し、意図した動作を変更して、そのルールを確認します。変更された実装を使うすべての箇所を追い直す代わりに、新しい要件に作業を絞れます。

バグ修正も同じです。`CancelOrder`が発送済みの注文も受理してしまうなら、修正版の`CancelUndispatchedOrder`を作成し、見落とされていたケースをテストし、呼び出し元を移行して、誤ったコマンドを無効にします。古い実装を固定することで、デプロイ時の状態は保たれますが、誤ったエントリーポイントを提供し続ける必要はありません。

## API全体をバージョン分けせずに動作を終了する

**利用者を移行する間、新旧の契約を共存させられます。** モバイルアプリは`PlaceOrder`で店頭受け取りを続け、ウェブサイトは`PlaceOrderWithContact`で配送を追加できます。在庫クエリや関係のないコマンドは、既存の名前と契約を維持します。

1つの操作が変わっただけでAPI全体を`/v2`に複製する必要はありません。変更した動作ごとに独自の識別子を付けます。すべての操作を同時に新しいAPIバージョンへ移すのではなく、利用者は準備ができた時点で置き換えを採用できます。

新しい利用者に選ばれないようにする古いコマンドやクエリには、**非推奨**の印を付けます。誰も呼び出していないことが利用状況からわかったら、そのエントリーポイントを無効化するか削除します。コマンドを終了しても、そこから記録されたイベントや、履歴の解釈に必要な定義は消えません。

## 共有コードを変更すると作業が増える理由

同じ配送先連絡先の要件を、既存の`POST /orders`エンドポイントと共有の`Order`モデルを編集する従来型アプリケーションで考えてみましょう。新しいフィールドを必須にすると、古いモバイル注文が動かなくなります。共有モデルにフィールドを追加すると、新しい注文ポリシーを求めていない注文編集画面やスタッフ画面にも影響します。

次に、キャンセルを単純な真偽値から、要求、受理、拒否を区別する状態に変えます。以前`cancelled`を確認していたコードはすべて見直さなければなりません。発送、在庫計算、お客様へのメールが対象になります。複数のフィーチャーで同じ変更可能なモデルを解釈しているため、小さな業務上の依頼が広がります。

**すでに動作していた箇所を見直す作業もコストに含まれます。** この図ではAからGまでがアプリケーションへの追加を表し、各Rは以前の動作で繰り返し発生する作業です。依存関係が積み重なるにつれて、変更ごとの作業が増える様子を曲線で示しています。

## 伸び方を線形に近づける

NeoHaskellでは、配送先連絡先の要件に合わせて、固定された注文契約の横に、名前付きのコマンドとそのルールを追加します。古い注文画面は既存の動作を続けます。新しいキャンセル方針も、明示的なスライスと契約として追加し、影響するクエリや統合をEvent Modelで確認できます。

**契約を安定させることで、新しい要件が既存の利用者すべての動作を黙って変えることを防げます。** スライスで実装作業を限定し、チャプターで業務の背景を保ち、モデルで新しい動作とアプリケーションの他の部分とのつながりを明らかにします。繰り返し共有コードを解きほぐすより、置き換えを作る方が簡単になるよう、NeoHaskellが共通の構造を用意します。

<GrowthComparison mode="bounded" />

追加ごとの作業がほぼ一定なら、開発全体の作業量は線形に近い形で増えます。同程度のスライスを追加するたび、同程度の作業が加わります。NeoHaskellはこの開発パターンを支えるよう設計されています。

キャンセル可能なタイミングについて、キャンセルは発送と整合している必要があります。その合意は、影響を受けるスライスの契約とルールに記述します。開発者は依存関係を明示し、確認し、テストできます。お客様の一連の体験が壊れてから気づく必要はありません。

## モデルを使ってコードを理解する

**NeoHaskell IDEではアプリケーションの構造を確認できます。** フィーチャーを開いてチャプターとスライスを見てから、コマンド、イベント、クエリ、統合のつながりをたどります。マグカップ店のモデルは実際のIDEで確認できます。

<IdeScreenshot />

キャンセルを変更するときは、Cancel orderチャプターから始めます。キャンセルを要求するコマンド、その結果として生成されるイベント、そのイベントを使う在庫クエリを確認します。それぞれの名前から、ソース内の対応する宣言を特定できます。既存プロジェクトの引き継ぎや、AIエージェントが作成した変更のレビューにも同じ方法が使えます。

視覚モデルはソースの宣言から生成されます。宣言を変更すると、IDEがモデルを更新します。コマンド名の変更やクエリとの新しい接続はアプリケーションの構造に属するため、誰かが別の図を手作業で保守しなくてもダイアグラムに反映されます。

## 仕様をアプリケーション内に保つ

**仕様はコードの一部です。** NeoHaskellのEvent Model DSLでは、フィーチャー、チャプター、スライス、コマンド、イベント、クエリ、統合を宣言します。スライスに記述するルールでは、Given、When、Thenのケースを含めて必要な動作を指定します。

以下はショップのモデルにあるキャンセルのチャプターです。この例では、別の箇所ですでに定義されているショップの`Order`、コマンド、イベント、クエリの型を使います。

```haskell
orders =
  feature "Orders" do
    chapter "Cancel order" do
      slice "Cancel before dispatch" do
        entity @Order do
          command @CancelOrder do
            produces @OrderCancelled

        rule "Cancel before dispatch" do
          orderId <- requestValue @Uuid
          given do
            event OrderPlaced {
              orderId = orderId,
              quantity = 1
            }
          when CancelOrder { orderId = orderId }
          therefore do
            event OrderCancelled {
              orderId = orderId,
              quantity = 1
            }

      slice "Show restored stock" do
        query @AvailableMugs do
          readsFrom @Order do
            onEvent @OrderPlaced
            onEvent @OrderCancelled
```

**ダイアグラムの階層とコードの階層は同じです。** チャプターにはコマンドスライスとクエリスライスが含まれます。`produces`はコマンドのイベントを宣言し、`readsFrom`と`onEvent`はクエリが参照する履歴を宣言します。在庫クエリは注文とキャンセルの両方を受け取り、両方の変更を回答に反映します。

ルールは、それが定めるコマンドの隣にあります。`requestValue`は、型付きの注文IDの例をルール実行側に求めます。`given`は受理された注文の履歴を用意し、`when`はキャンセルコマンドを指定します。`therefore`はDSLのThenにあたり、期待する`OrderCancelled`イベントを示します。判断の実装には、満たすべき具体的なケースがあります。

発送済みの注文を扱う2つ目のルールでは、キャンセルを拒否し、在庫を変えないことを確認します。在庫クエリのスライスでは、受理されたキャンセルによって利用可能数が戻ることを別途確認します。それぞれのケースは、対応する動作と一緒に置きます。

独立したMarkdownファイルやConfluenceページは、アプリケーションを変更した後に誰かが更新しなければ古くなります。NeoHaskellでは、モデルとルールをソース内に宣言します。その宣言から仕様書を生成できるため、保守が必要な別の情報源になりません。
