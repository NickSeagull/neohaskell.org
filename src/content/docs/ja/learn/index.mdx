[数値の背後にある事実を残す](../introduction/history/#record-what-happened)のマグカップ店では、受理された注文をイベントとして記録し、それを使って利用可能な在庫を計算します。

イベントは、アプリケーションが受け入れた事実です。そのため、イベントの境界は重要です。お客様は`OrderPlaced`イベントを送るだけで、店が注文を受理したことにはできません。

在庫が3個しかないのに、お客様が4個を求めたとします。**注文を要求することと、受理された注文があることは別です。** アプリケーションはリクエストを受け取り、確認し、在庫を消費せずに拒否できなければなりません。

## コマンドで変更を要求する <a id="ask-for-a-change-with-a-command" />

**コマンド**はアプリケーションを変更する意図を表します。`PlaceOrder`には、注文を要求するために必要な情報を含めます。マグカップ1個なら、次のようになります。

```haskell
PlaceOrder {
  product = "ceramic mug",
  quantity = 1
}
```

**判断**は、現在の状態とショップの方針に照らしてコマンドを評価します。数量は正の値で、在庫が足りている必要があります。在庫が3個なら、1個の注文は受理され、4個の注文は拒否されます。

<EventModelTour kind="decision" />

受理すると`OrderPlaced`を記録します。拒否した場合は在庫を変えず、`OrderPlaced`イベントも記録しません。**コマンドは意図を伝え、イベントは受理された事実を記録します。**

NeoHaskellは、関連する状態を取得して判断を評価し、受理されたイベントを追記する実行経路を提供します。開発者は店の約束を表す条件を書きます。ウェブサイトとAIツールは同じコマンドを送信し、同じ判断を利用できます。

## 業務上の判断を純粋にする <a id="make-business-decisions-pure" />

**NeoHaskellでは、純粋なコードをアプリケーション開発の中心に置いています。** 業務ロジックは、受け取った情報から何をすべきかを記述します。判断はコマンドと現在の状態を確認し、受理または拒否を示します。データベース接続を開いたり、確認メールを送ったり、決済プロバイダーを呼び出したりすることはできません。

店の在庫ルールでは、同じ注文と在庫数に対して、受理または拒否という同じ結果が出ます。在庫が3個のとき4個の注文が可能かをテストしても、データベースに注文は作られません。判断の答えを計算するだけです。

この境界によって、日々の開発が変わります。

- **外部への影響を生まずに、何千ものケースをテストできます。** 在庫数と要求数量の組み合わせを生成し、ゼロ、負の値、最後の1個も含めて確認できます。データベース、ネットワーク接続、メールアカウントは不要です。
- **障害を再現できます。** 在庫ルールの不具合を見つけた入力を保存して、再実行できます。ルールを調べるときに、プロバイダーの稼働状況やテストデータベースの中身に左右されません。
- **観測できる動作を基準にリファクタリングできます。** 古い在庫ルールと新しい在庫ルールに同じケースを与え、判断を比較します。人やAIエージェントが書いた変更を、ショップの約束に照らして確認できます。
- **方針を書き直さずにインフラを変更できます。** 在庫ルールにSQLやメールプロバイダーの呼び出しはありません。ストレージやメールサービスを交換しても、注文を受理する条件はそのままです。
- **ロジックを理解し再利用できます。** 入力と結果の判断を読み、別のサービスに隠れた書き込みを追わずに済みます。データベース接続に依存させずに、計算を切り出したりルールを再利用したりできます。

**NeoHaskellでは、純粋なアプリケーションロジックが標準です。** 開発者がルールと計算を書き、言語が状態を読み込み、受理された変更を記録する仕組みを提供します。各ルールの周囲でその仕組み全体を実行しなくても、業務動作をテストできます。

## アプリケーションが役に立つ仕事をするには <a id="how-does-the-application-do-useful-work" />

受理された注文でも、確認メールが必要です。**統合はアプリケーションのロジックの外で処理を実行します。** その作業を分けて構成することで、店の判断を実行プロバイダーに依存させません。

統合ワーカーは、自分のタスクの実行方法を知っています。メールワーカーは宛先とメッセージを受け取り、送信します。注文の許可、残りの在庫数、確認メールの送信先は判断しません。それらはアプリケーションの純粋なロジックで決めます。

`OrderPlaced`を記録した後、アプリケーションからメール送信を依頼できます。メールプロバイダーが利用できなくても、注文は受理されたままです。メールの配信方法を変える場合に変更するのは統合であり、在庫方針ではありません。[統合ガイド](../guides/integrations/)では、ワーカーの構成と実行方法を説明します。

## 各画面に必要な回答を用意する <a id="give-each-screen-the-answer-it-needs" />

注文が受理されると、立場によって必要な回答が異なります。次のお客様は利用できる在庫を知りたいでしょう。注文したお客様には確認が必要です。スタッフは、対応が必要な注文数を知る必要があります。

**クエリ**はアプリケーションの状態から導いた情報を維持し、呼び出し元に回答を返します。マグカップ3個から始めたショップで、1個の注文を受理すると、次の回答が得られます。

在庫の回答を読むことによって、新しい注文が入るわけではありません。ページを開くたびにイベント履歴全体を走査する必要もありません。NeoHaskellは変更が届くたびにクエリ状態を更新し、画面は維持された回答を読み取ります。

**同じ事実から、異なる質問に答えられます。** お客様向け表示とスタッフ向けレポートで形式を変えても、起きたことの記録を分ける必要はありません。新しいレポートを、保持された履歴から計算することもできます。

画面に表示された回答は、新しい変更の反映に遅れが出る場合があります。そのため、画面上の在庫数だけで注文できるとは限りません。リクエストが届いた時点で、コマンドの判断が関連する状態を確認します。

変更と質問を分ける考え方を**CQRS**と呼びます。コマンドと判断は、起こりうることを制御します。クエリは人々が知りたい情報をまとめます。Event Sourcingは、アプリケーションが状態を導出するための履歴を提供します。
