Количество товара сообщает следующему покупателю, сколько кружек доступно. **События объясняют, из-за чего это число изменилось.**

Вспомните магазин кружек из материала [Работа за кодом](/introduction/#the-questions-that-change-the-software), где просьба добавить онлайн-заказы вызвала вопросы об обещаниях магазина покупателям.

В магазине три кружки. Принятие заказа на одну резервирует её для покупателя, и остаются две доступные кружки.

<EventModelTour kind="story" />

Число на складе даёт следующему покупателю полезный ответ. **Но оно не объясняет, почему ответ изменился.** Разбитая кружка также уменьшит запас с трёх до двух, но магазину не придётся готовить заказ.

## Записывайте произошедшее

Если сохранять только последнее значение запаса, это различие теряется. NeoHaskell записывает бизнес-факт, вызвавший изменение: заказана одна керамическая кружка. Такой записанный факт называется **событием**.

Название события передаёт смысл. `OrderPlaced` сообщает приложению, что магазин принял заказ. Разбитая кружка требует другого события, поскольку это другая работа, даже если доступный запас изменился так же.

**Запись событий сохраняет бизнес-смысл изменения.** Разработчик явно выбирает этот смысл, вместо того чтобы оставлять кому-то на будущее задачу восстановить его по числу на складе.

## Вычисляйте настоящее по прошлому

В NeoHaskell **события служат источником истины для состояния приложения**. Чтобы вычислить доступный запас, начните с нуля и проследите произошедшее: магазин получил три кружки, затем принял заказ на одну. Результат - две доступные кружки. Вывод состояния из записанных событий называется **Event Sourcing**.

Допустим, покупатель затем отменяет заказ до отправки, а магазин возвращает кружку в доступный запас. Приложение записывает `OrderCancelled`, и доступное количество снова становится равным трём. Исходное событие заказа тоже сохраняется. История отменённого заказа отличается от истории заказа, которого никогда не было.

Исправления следуют тому же принципу: запишите исправление и примените его эффект. Чтобы изменить настоящее, не нужно переписывать рассказ о том, как оно наступило.

История также позволяет исправлять вычисления. Если в расчёте запаса есть ошибка, исправьте её и снова примените историю, чтобы восстановить производное состояние. **Повторное проигрывание пересчитывает состояние**, а не размещает заказ и не списывает деньги с покупателя повторно.

## Разве всё не замедлится, когда история вырастет?

История растёт по мере использования приложения, но **NeoHaskell не начинает с первого события при каждой операции**. Оно хранит уже вычисленное состояние и применяет последующие изменения начиная с него. Для чтения ответа используются поддерживаемые данные, а не повторное проигрывание всей истории при каждом посещении страницы.

Эта работа происходит внутри языка. Приложение сохраняет сведения о произошедшем, не пересчитывая все прежние заказы при каждом новом.

## Сохраняйте факты, нужные для будущих вопросов

Благодаря событиям заказа и отмены магазин может отличить продажи от отмен, даже если оба варианта приводят к такому же конечному запасу, как отсутствие активности. По записанным фактам можно расследовать заказ или создать новый отчёт.

Поэтому проектирование событий помогает понять бизнес. Если сотрудникам нужно знать, кто одобрил исключение, это должно быть отражено в событии. **Подумайте, что кому-то понадобится объяснить позже.** Ответ на этот вопрос определяет, что приложение запоминает сегодня.
