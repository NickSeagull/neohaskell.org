Магазин кружек из материала [Храните факты, стоящие за числами](../introduction/history/#record-what-happened) записывает принятые заказы как события и использует их для вычисления доступного запаса.

Событие - факт, принятый приложением. Поэтому важно определить его границы: покупатель не может объявить, что магазин принял заказ, просто отправив событие `OrderPlaced`.

Представьте, что покупатель заказывает четыре кружки, когда осталось только три. **Запросить заказ и получить принятый заказ - не одно и то же.** Приложению нужно получить запрос, проверить его и отказать, не расходуя запас.

## Запросите изменение командой <a id="ask-for-a-change-with-a-command" />

**Команда** выражает намерение изменить приложение. `PlaceOrder` содержит данные для запроса заказа. Для одной кружки данные выглядят так:

```haskell
PlaceOrder {
  product = "ceramic mug",
  quantity = 1
}
```

**Решение** оценивает команду с учётом текущего состояния и правил магазина. Количество должно быть положительным, а товара должно хватать. Если в запасе три кружки, заказ на одну будет принят, а на четыре - отклонён.

<EventModelTour kind="decision" />

Принятие записывает `OrderPlaced`. При отклонении запас не меняется, а событие `OrderPlaced` не записывается. **Команда несёт намерение, а событие фиксирует принятый факт.**

NeoHaskell предоставляет путь выполнения: получить нужное состояние, оценить решение и добавить принятые события. Разработчик пишет условия, выражающие обещание магазина. Сайт и инструмент ИИ могут отправить одну и ту же команду и использовать то же решение.

## Принимайте бизнес-решения чистым кодом <a id="make-business-decisions-pure" />

**NeoHaskell ставит чистый код в центр разработки приложений.** Бизнес-логика описывает, что должно произойти исходя из полученной информации. Решение проверяет команду и текущее состояние, а затем описывает принятие или отклонение. Оно не может открыть подключение к базе данных, отправить письмо с подтверждением или вызвать платёжного провайдера.

При проверке правила запасов одинаковые заказ и доступный запас приводят к одинаковому принятию или отклонению. Тест того, можно ли заказать четыре кружки при запасе в три, не создаёт заказ в базе данных. Он вычисляет ответ решения.

Эта граница меняет повседневную разработку:

- **Проверяйте тысячи случаев без внешних последствий.** Создавайте сочетания запаса и запрошенного количества, включая ноль, отрицательные значения и последнюю доступную кружку. Проверяйте решения без базы данных, сети или почты.
- **Воспроизводите ошибки.** Сохраните входные данные, выявившие сбой правила запасов, и запустите их снова. Для расследования этого правила не требуется доступный провайдер или правильно заполненная тестовая база данных.
- **Рефакторите, сравнивая наблюдаемое поведение.** Проверьте старое и новое правила запасов на одних и тех же случаях и сравните решения. Изменения, написанные вручную или ИИ-агентом, можно проверить на соответствие обещаниям магазина.
- **Меняйте инфраструктуру, не переписывая правила.** В правиле запасов нет SQL-вызовов и обращений к почтовому провайдеру. Замена хранилища или почтовой службы не меняет условия принятия заказа.
- **Понимайте и повторно используйте логику.** Просматривайте входные данные и итоговое решение, не отслеживая скрытые записи в других сервисах. Выделяйте вычисления или используйте правило повторно без подключения к базе данных.

**В NeoHaskell чистая логика приложения - обычный способ разработки.** Разработчик пишет правила и вычисления; язык предоставляет средства для загрузки состояния и записи принятых изменений. Для тестирования бизнес-поведения не нужно запускать всю эту инфраструктуру вокруг каждого правила.

## Как приложение выполняет полезную работу? <a id="how-does-the-application-do-useful-work" />

Для принятого заказа всё ещё нужно отправить письмо с подтверждением. **Интеграции выполняют эффекты за пределами логики приложения.** Они обособляют эту работу, чтобы решения магазина не зависели от провайдера, который её выполняет.

Обработчик интеграции умеет выполнять свою задачу. Почтовый обработчик получает адресата и сообщение, а затем отправляет его. Он не решает, разрешён ли заказ, сколько товара осталось и какие покупатели должны получить подтверждение. Эти решения принадлежат чистой логике приложения.

Приложение может запросить эту работу после записи `OrderPlaced`. Если почтовый провайдер недоступен, заказ остаётся принятым. Изменение способа отправки письма меняет интеграцию, а не правила учёта запасов. В [руководствах по интеграциям](../guides/integrations/) описана настройка и запуск этих обработчиков.

## Предоставляйте каждому экрану нужный ответ <a id="give-each-screen-the-answer-it-needs" />

После принятия заказа разным людям нужны разные ответы. Следующему покупателю нужен доступный запас. Покупателю нужен ответ о заказе. Сотрудникам нужно знать, сколько заказов ждут их внимания.

**Запрос** поддерживает полезную информацию, полученную из состояния приложения, и предоставляет ответ вызывающему. Для магазина, начавшего с трёх кружек и без заказов, принятие заказа на одну кружку даёт такие ответы:

Чтение ответа о запасах не оформляет другой заказ. Для этого также не нужно заново просматривать всю историю событий при каждом посещении страницы: NeoHaskell обновляет состояние запроса по мере поступления изменений, а экран читает поддерживаемый ответ.

**Одни и те же факты могут отвечать на разные вопросы.** Для экрана покупателя и отчёта сотрудников можно задать разную структуру, не создавая несовпадающих историй произошедшего. Новый отчёт может вычислить другой ответ по сохранённой истории.

Отображаемый ответ может запаздывать относительно нового изменения. Поэтому показанное на экране число товара не разрешает оформить заказ: решение команды проверяет актуальное состояние при получении запроса.

Разделение изменений и вопросов называется **CQRS**. Команды и решения определяют, что может произойти; запросы организуют нужную людям информацию. Event Sourcing предоставляет историю, из которой приложение выводит своё состояние.
